- (constraint) Platform: DigitalOcean Basic Droplet — 1 vCPU / 1 GB RAM / 25 GB Disk. FastAPI runs with 2 uvicorn workers. This is a hard compute ceiling for the lifetime of this feature.
- (constraint) Parent architecture (architecture.md) is binding and read-only. All ADs, naming conventions, job-durability pattern (job record before BackgroundTask), rate limiting (slowapi 10 req/min/user), error shape, and service boundaries inherited.
- (direction) User intent: add Voice-to-text as an alternative Brain Dump input method (Phase 2). Key concern: concurrent users on constrained Droplet.
- (decision) AD-V1: Transcription is external-only. Binds: transcription service. Prevents: two builders choosing local vs remote (local Whisper tiny model = 250-500 MB RAM + blocks single vCPU 10-30s per request = OOM + concurrency kill on 1 GB Droplet). Rule: all speech inference delegated to external API via httpx; zero STT compute on Droplet. [ASSUMPTION: OpenAI Whisper API — alternative is Google Cloud STT if single-vendor Google preference]
- (decision) AD-V2: Transcription endpoint is synchronous async (no BackgroundTask, no job record). Binds: POST /api/v1/voice/transcribe. Prevents: unnecessary job-record overhead for a pure I/O proxy; also prevents blocking a uvicorn worker. Rule: endpoint MUST be async def + await httpx call; MUST NOT spawn BackgroundTask; MUST NOT create a job record. Rationale: asyncio handles N concurrent 'await httpx.post(...)' without blocking; Whisper API returns in 2-10s for typical brain-dump lengths; job-table overhead is disproportionate for a stateless I/O call. This is an explicit, narrow exemption from the parent job-durability pattern.
- (decision) AD-V3: Audio bytes never persisted. Binds: entire audio pipeline. Prevents: audio landing in Supabase Storage or on Droplet disk. Rule: UploadFile bytes travel in-process from FastAPI multipart parser to external transcription API call; never written to disk, Supabase Storage, or any DB column. Audio is an input modality, not a content artifact.
- (decision) AD-V4: Transcript text rejoins the existing pipeline at the Brain Dump textarea boundary. Binds: frontend integration, data model, backend. Prevents: voice path creating a new campaign field, a new job type, or a schema migration. Rule: POST /api/v1/voice/transcribe returns {transcript: string}; frontend fills the existing BrainDumpInput textarea with transcript text; user may edit; campaign creation proceeds identically to typed input via existing POST /api/v1/campaigns. No DB migration.
- (decision) AD-V5: Browser audio capture via MediaRecorder API only; Web Speech API is banned. Binds: VoiceBrainDump.tsx. Prevents: builders using Web Speech API (Chrome-only, routes audio to Google without user awareness, produces no file blob, incompatible with server-side transcription). Rule: capture via MediaRecorder; emit Blob MIME type audio/webm;codecs=opus (Chrome/Firefox) or audio/mp4 (Safari); send MIME type in multipart Content-Type; transcription provider must accept both natively.
- (decision) AD-V6: Hard size cap and dedicated rate limit at FastAPI layer. Binds: POST /api/v1/voice/transcribe. Prevents: RAM exhaustion from large uploads and runaway API costs. Rule: reject Content-Length > 10 MB with HTTP 413; enforce separate slowapi limit of 5 transcription requests/hour/user (in addition to existing global 10 req/min/user). 10 MB cap ~ 4-5 min at Opus 32kbps — sufficient for any brain dump. [ASSUMPTION: 5/hour is the right cost/UX balance — revisit post-launch]
- (event) ARCHITECTURE-SPINE.md distilled from memlog and written. Status: draft. Awaiting Boris review.
- (decision) AD-V1 REVISED: OpenAI ruled out. Google Cloud STT also ruled out for long recordings: its async batch API (longrunningrecognize / BatchRecognize) requires audio in GCS, which conflicts with AD-V3 (no audio storage). Ruling: provider must accept direct audio upload with no intermediate cloud storage. Decision: Deepgram POST /v1/listen (pre-recorded) — single HTTP call, returns transcript synchronously from their side, real-time factor ~0.1-0.3x (10-min audio → 1-3 min processing), accepts WebM/Opus and MP4 natively. Wrapped in BackgroundTask — no issue holding the background HTTP call open. [ASSUMPTION: Deepgram as provider; AssemblyAI is acceptable alternative with same AD-V3 compliance]
- (decision) AD-V2 REVISED: For long brain-dump recordings (target: up to ~15 min), switch to BackgroundTask + job record — consistent with parent job-durability pattern. POST /api/v1/voice/transcribe returns 202 {job_id}. BackgroundTask: stream audio to Deepgram, await transcript, write result to jobs.result JSONB, update job status to complete. Frontend polls GET /api/v1/jobs/{job_id} (existing pattern). When status=complete, reads job.result.transcript and fills BrainDumpInput textarea. DB migration: add one nullable result JSONB column to jobs table. This is the ONLY schema change for Phase 2.
- (constraint) AD-V3 confirmed by user: audio bytes never persisted on PersonnaPress infrastructure. Deepgram handles audio transiently as part of their service — this is acceptable. Provider transience is not a violation of AD-V3.
- (decision) AD-V1 FINAL: Groq API free tier — whisper-large-v3-turbo via https://api.groq.com/openai/v1/audio/transcriptions. Boris confirmed: no paid APIs. Groq free tier (~7,200 req/day) is sufficient for early-stage; OpenAI-compatible request format means minimal code change from earlier drafts. Local faster-whisper ruled out: CPU-bound on 1 vCPU, 2-5x real-time = 20-50 min for a 10-min brain dump, blocks all concurrent requests. Browser-side Whisper ruled out: unreliable on weak/mobile devices, ~140 MB first-load, changes architecture. New env var: GROQ_API_KEY. Integration file renamed: integrations/groq_audio.py.
