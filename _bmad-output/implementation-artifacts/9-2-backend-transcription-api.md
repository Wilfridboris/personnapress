# Story 9.2: Backend Transcription API

Status: done

## Story

As a developer,
I want the complete backend transcription infrastructure in place — DB migration, Groq integration, service, BackgroundTask worker, and FastAPI route,
So that audio files submitted by the frontend are securely transcribed by Groq's API and results are retrievable via the existing job polling endpoint.

## Context & Motivation

This is Story 9.1 from the epics file (numbered 9.2 in sprint status because `9-1-production-launch-infrastructure` is already done). It implements the server-side half of the Voice-to-text Brain Dump feature: a new `POST /api/v1/voice/transcribe` endpoint that accepts audio uploads, creates a job record, and delegates transcription to Groq Whisper via a BackgroundTask. The frontend polls the existing `GET /api/v1/jobs/{job_id}` endpoint to retrieve the transcript once complete.

**Architecture paradigm:** Stateless I/O Proxy. Audio bytes travel in-process from the FastAPI multipart parser → BackgroundTask → Groq API → discarded. They are NEVER written to disk, Supabase Storage, or any DB column.

**Zero new Python packages.** Groq REST API is called via the existing `httpx` dependency.

**The only schema change in this entire feature** is one new nullable `result JSONB` column on the `jobs` table.

### AC 4 — Groq integration: `groq_audio.py`

**Given** `backend/app/integrations/groq_audio.py` is called with valid audio bytes and a supported MIME type,
**When** `await transcribe(content: bytes, mime_type: str) -> str` executes,
**Then** it POSTs to `https://api.groq.com/openai/v1/audio/transcriptions` via `httpx.AsyncClient` with:
- `Authorization: Bearer {GROQ_API_KEY}` header
- `model = "whisper-large-v3-turbo"` field in the multipart form
- The audio bytes sent as the `file` field with the provided MIME type as content type
**And** it returns the `transcript` string from the response JSON on success.
**And** it raises a descriptive exception on Groq API failure (non-2xx response or network error).
**And** no other module in the codebase calls the Groq audio endpoint directly — all Groq audio calls originate exclusively from this function.

### AC 5 — Voice service: `services/voice.py`

**Given** `backend/app/services/voice.py` is called with valid audio `content: bytes` and `content_type: str`,
**When** the service processes the request,
**Then** for an unsupported MIME type it raises `HTTPException(415, detail={...AUDIO_FORMAT_UNSUPPORTED...})` **before** creating any job record.
**And** for a supported MIME type it creates a `jobs` row with `job_type='transcription'`, `status='pending'`, `campaign_id=None`, `client_id=None`.
**And** it returns `(job_id, audio_bytes, mime_type)` to the caller so the router can dispatch the BackgroundTask.

The service validates MIME type against the exact allowlist: `{"audio/webm", "audio/webm;codecs=opus", "audio/mp4", "audio/mpeg", "audio/wav"}`.

### AC 6 — Transcription worker: `workers/transcribe.py`

**Given** `backend/app/workers/transcribe.py` `run_transcription(job_id, audio_bytes, mime_type)` BackgroundTask is dispatched,
**When** it executes,
**Then** it creates its own `AsyncSessionLocal()` session (not the request-scoped session, which is closed before BackgroundTasks run — see existing `workers/generate.py` pattern).
**And** it fetches the job record, sets `status='in_progress'` and `started_at=utcnow()`, then calls `await groq_audio.transcribe(audio_bytes, mime_type)`.
**And** on success: sets `job.result = {"transcript": "<transcript_string>"}`, `job.status = "complete"`, `job.completed_at = utcnow()`, commits.
**And** on failure (Groq API 5xx or 429): retries up to 3 consecutive attempts total. After 3 failed attempts: sets `job.error_details` to a descriptive message and `job.status = "failed"`, commits.
**And** `audio_bytes` bytes are released from memory after the httpx call completes — they are NOT written to disk, Supabase Storage, or any database column at any point.
**And** any unhandled exception is caught at the outer try/except, logged with `logger.exception(...)`, and captured via `sentry_sdk.capture_exception(exc)` (same pattern as `workers/generate.py`).

### AC 7 — Router: `routers/voice.py`

**Given** an authenticated user sends `POST /api/v1/voice/transcribe` with valid audio and `Content-Length ≤ 10,485,760`,
**When** the route processes it,
**Then** it checks `Content-Length` header BEFORE reading the request body.
**And** it calls the service (which validates MIME, creates job, returns `(job_id, audio_bytes, mime_type)`).
**And** it dispatches `background_tasks.add_task(run_transcription, job_id=job.id, audio_bytes=audio_bytes, mime_type=mime_type)`.
**And** it commits the DB session (job record must be persisted before BackgroundTask runs — job-durability pattern).
**And** it returns `JSONResponse(status_code=202, content={"job_id": str(job.id)})`.

**Given** `Content-Length > 10,485,760` (10 MB),
**When** the route receives it,
**Then** returns HTTP 413 with `{"error": {"code": "AUDIO_TOO_LARGE", "message": "Audio file exceeds the 10 MB limit.", "detail": {}}}` before reading the request body.

**Given** a user has exceeded the rate limit (5 transcription requests/hour/user),
**When** the slowapi rate limit decorator triggers,
**Then** returns HTTP 429. The rate limit key function extracts `user_id` from the JWT cookie (not remote IP, unlike the global limiter — this is a per-user limit).

**Given** an unauthenticated request,
**When** `get_current_user` dependency runs,
**Then** HTTP 401 is returned (inherited — no new auth logic).

### AC 8 — Router registered in `main.py`

**Given** `backend/app/main.py` is reviewed,
**When** the router list is inspected,
**Then** `voice.router` is imported from `app.routers` and registered with `app.include_router(voice.router, prefix=API_PREFIX)`.

### AC 9 — No new packages

### Background Task Pattern (critical)

Look at `workers/generate.py` for the authoritative pattern:
- Worker creates its own `async with AsyncSessionLocal() as db:` — the request-scoped session is closed before BackgroundTasks execute.
- Worker checks job status is `'pending'` before proceeding.
- Errors caught at outermost try/except, logged with `logger.exception`, captured by Sentry.

For `run_transcription`, the signature is:
```python
async def run_transcription(job_id: uuid.UUID, audio_bytes: bytes, mime_type: str) -> None:
```

The `audio_bytes` are passed directly (not re-fetched from DB — they were never persisted).

### Retry Logic in Worker

The story requires retrying Groq calls up to 3 total attempts on 5xx or 429 responses. Pattern:

```python
for attempt in range(3):
    try:
        transcript = await groq_audio.transcribe(audio_bytes, mime_type)
        # release bytes now — they are no longer needed
        audio_bytes = b""
        break
    except SomeGroqError:
        if attempt == 2:
            # set failed, commit, return
```

### Writing `result` to the Job

The `update_job` repository function in `jobs.py` does NOT include `result` in its allowed field set. Do NOT use `update_job` for this — instead, directly assign and commit:

```python
job.result = {"transcript": transcript}
job.status = "complete"
job.completed_at = utcnow()
await db.commit()
```

This is the same direct-assignment pattern already used throughout the codebase for model mutations.

### Rate Limiting by `user_id`

The global `limiter` in `app/core/rate_limit.py` uses `key_func=get_remote_address`. The voice endpoint needs to key on `user_id` from the JWT to enforce a per-user limit. Define a custom key function in `routers/voice.py`:

```python
from app.core.jwt_utils import decode_access_token  # or however JWT is decoded in auth.py

def _voice_rate_key(request: Request) -> str:
    """Rate limit by user_id extracted from JWT cookie; fall back to IP."""
    try:
        token = request.cookies.get("access_token", "")
        payload = decode_access_token(token)  # look at how auth.py/dependencies.py decodes it
        return str(payload.get("user_id", "")) or get_remote_address(request)
    except Exception:
        return get_remote_address(request)
```

Then on the route: `@limiter.limit("5/hour", key_func=_voice_rate_key)`.

Look at `backend/app/core/dependencies.py` and `backend/app/core/auth.py` (or equivalent) to see the exact JWT decode function and cookie name used by `get_current_user`. Mirror it exactly.

### Size Check Before Body Read

FastAPI reads the full request body into memory before the route handler runs if you use `UploadFile`. To enforce the size cap BEFORE reading, check the `Content-Length` header first:

```python
async def transcribe_audio(
    request: Request,
    file: UploadFile,
    background_tasks: BackgroundTasks,
    current_user: dict = Depends(get_current_user),
    db: AsyncSession = Depends(get_session),
):
    content_length = request.headers.get("content-length")
    if content_length and int(content_length) > 10_485_760:
        raise HTTPException(
            status_code=413,
            detail={"error": {"code": "AUDIO_TOO_LARGE", "message": "Audio file exceeds the 10 MB limit.", "detail": {}}},
        )
    content = await file.read()
    # re-check actual size after read (client could lie about Content-Length)
    if len(content) > 10_485_760:
        raise HTTPException(...)
```

### Error Response Shape

All errors in this router use the established project error shape:
```python
raise HTTPException(
    status_code=4xx,
    detail={"error": {"code": "ERROR_CODE", "message": "Human-readable.", "detail": {}}},
)
```
Error codes: `AUDIO_TOO_LARGE` (413), `AUDIO_FORMAT_UNSUPPORTED` (415), `TRANSCRIPTION_RATE_LIMITED` (429).
HTTP 503 with `TRANSCRIPTION_FAILED` is set in the worker's `job.error_details` field, not as an HTTP error — the router always returns 202.

### Groq API Call Details

Endpoint: `POST https://api.groq.com/openai/v1/audio/transcriptions`
Auth: `Authorization: Bearer {settings.GROQ_API_KEY}`
Model: `whisper-large-v3-turbo`
Request: multipart form with fields `file` (audio bytes with MIME type) and `model`.

```python
async with httpx.AsyncClient(timeout=120.0) as client:
    response = await client.post(
        "https://api.groq.com/openai/v1/audio/transcriptions",
        headers={"Authorization": f"Bearer {settings.GROQ_API_KEY}"},
        data={"model": "whisper-large-v3-turbo"},
        files={"file": ("audio", content, mime_type)},
    )
response.raise_for_status()
return response.json()["text"]
```

Groq free tier: ~7,200 audio-seconds/day. `whisper-large-v3-turbo` processes audio at ~10–30s regardless of recording length on Groq's LPU — hence the 202/async pattern.

### Job Ownership Gap (Known — Do Not Fix in This Story)

Transcription jobs have neither `campaign_id` nor `client_id` set. The existing `GET /api/v1/jobs/{job_id}` ownership check falls through to returning the job without user verification when both are NULL. Since job IDs are UUIDs (122 bits of entropy), the practical security risk is negligible. This is a known gap — document it with a `# TODO: link transcription jobs to user_id` comment in the router and do not add a `user_id` column to the `jobs` table in this story (that would require a new migration and is out of scope).
